# ExpW: локальный контроллер на сервере, робот за Wi-Fi

Вопрос: что происходит со складским роботом, если навигатор и локальный планировщик (MPPI или DWA, 10 Гц) работают на сервере, а Wi-Fi даёт задержку, потери пакетов и обрывы связи? Какие дешёвые стратегии на стороне робота сохраняют безопасность и скорость?

Всего 2754 эпизода в MuJoCo: TurtleBot3 Burger, лидар, сценарии `bypass`, `blocked` и `open`, скорости `v_max = 0.22` и `0.6` м/с (`MPP_MAX_V`). Исходники `mpp` не менялись. Весь код лежит в `expW/`.

## Модель

**Цикл.** Робот работает на 20 Гц (шаг 50 мс), сервер на 10 Гц, как `control_dt = 0.1` в `run_episode`. Цикл скопирован из `run_episode` (`netsim.py`). Коробки проверяются только на тиках 10 Гц, как в оригинале. Поэтому при `d = 0` результат совпадает бит в бит.

**Uplink, 10 Гц.** В каждом пакете метка времени, поза, скорость и ack версии пути. Скан (360 лучей, 5 Гц) идёт в каждом втором пакете. Сервер видит позу и карту с опозданием `d`. Потерянный скан для сервера пропадает навсегда (UDP, без повторной отправки).

**Сервер.** Работает по событиям: `nav.tick` вызывается только на тике, где пришло новое состояние. Компенсации задержки на сервере нет (наивный сервер).

**Downlink.** Команда или последовательность приходит на робот через `d`.

**Канал.** `d` задаёт задержку в одну сторону, то есть RTT = 2d. Задержка постоянная, без джиттера. Потери i.i.d. с вероятностью `p`, независимо по направлениям. Обрывы задаёт модель Гилберта–Эллиотта: одно общее состояние для обоих направлений, средняя длина обрыва 0.5 или 2 с, около 10 % времени. Отдельно есть детерминированный обрыв на 2 с ровно в момент падения коробки (`drop@box2s`; в `open`, где коробки нет, обрыв начинается на t = 8 с).

**Стратегии робота**

- **S0.** Робот держит последнюю команду бесконечно.
- **S1.** Держит её 0.5 с после последнего пакета, затем стоп, как таймаут `cmd_vel` в Nav2.
- **S2.** Буфер траектории. Сервер шлёт всю оптимальную последовательность MPPI (`U`, 2.5 с) с меткой времени того состояния, по которому она посчитана. Робот исполняет `U[floor((t - stamp)/dt)]` и останавливается, когда буфер кончился. DWA шлёт свою команду, повторённую на горизонт 1.7 с. Команды отъезда назад и стопа держатся 0.5 с после ожидаемого прихода.
- **S3.** S2 плюс бортовая проверка. Следующие 0.5 с буфера прокатываются по собственной свежей лидарной костмапе робота. Если зазор окажется меньше `r + 1 см` (или меньше текущего зазора, если робот уже ближе), робот встаёт.
- **S4.** S3 плюс бортовой fallback. Если пакетов нет дольше 0.3 с, на роботе включается DWA (вариант: MPPI с K = 16) и ведёт по последнему полученному глобальному пути. Путь передаётся по downlink с ack, прореженный до 20 см. Как только приходит пакет, управление возвращается серверу.

**Метрики.**

- `success`: сервер объявил цель достигнутой, итоговая ошибка до цели не больше 0.3 м, ноль контактов.
- Контакты: эпизоды с контактом и число событий контакта. Число событий раздуто, когда робот «бодает» стеллаж, поэтому смотреть стоит в первую очередь на число эпизодов.
- `min gap`: минимальный зазор по истинной карте с упавшими коробками. Отрицательный зазор значит, что робот въехал в стеллаж.
- Время до цели: медиана по успешным эпизодам. Здесь есть смещение отбора: если успешных эпизодов мало, медиана получается по «лёгким» случаям.
- Время стояния: истинная скорость около нуля до конца эпизода.
- Байты в секунду: заголовок 42 Б на пакет, скан 1440 Б (float32), команда 8 Б, последовательность MPPI 25 × 8 = 200 Б.

**Сиды и сетка.** Сиды 1–3 для детерминированных каналов и 1–6 для случайных (потери и GE). DWA и лидар без шума детерминированы. Поэтому для DWA на каналах без случайности три сида дают один и тот же эпизод, фактически n = 1 на сценарий. У MPPI сид меняет сэмплирование.

**Проверка.** При `d = 0, p = 0` все стратегии совпадают с обычным `run_episode`: **162 из 162 эпизодов идентичны** (успех, время ±0.05 с, зазор ±2 мм) для MPPI и DWA на обеих скоростях.

## Главные выводы

1. **Задержка опаснее потерь, а лечит её буфер траектории с меткой времени (S2).** Наивный сервер с наивным роботом (S0/S1) замыкает обратную связь через RTT. Робот начинает рыскать, на 0.6 м/с время растёт вдвое уже при RTT 100 мс (33 → 67 с). При RTT 300 мс успешны 56 % эпизодов, при 600 мс ни одного. Типичный отказ выглядит так: робот прижимается к стеллажу у коробки, MPPI не находит допустимой траектории, отъехать назад навигатор не может, и после 40 перепланирований всё заканчивается `failed`. S2 исполняет `U` по индексу «сейчас минус метка состояния», то есть по сути компенсирует задержку разомкнутым исполнением плана. Это держит 100 % успеха и почти базовое время до RTT 600 мс (d = 300) на обеих скоростях. А i.i.d. потери даже 20 % на MPPI почти безвредны: 94–100 % успеха.
2. **Бортовая проверка безопасности (S3) единственная убирает контакты полностью.** В 540 эпизодах S3 и S4 с MPPI и 270 эпизодах S3 с DWA на всех каналах не было ни одного контакта. Стоит она 0.05–0.08 мс на вызов. У DWA буфер почти бесполезен: команда постоянная, при чистой задержке S2 = S0. Зато S3 поднимает DWA на 0.6 м/с с 53 % до 93 % успеха. **Отрицательный результат:** при RTT 1.2 с (d = 600) S3 превращает столкновения в stop-and-go. Робот безопасен, но медленный: 0.6 м/с даёт 73.6 с против 33, а при 0.22 м/с всего 4 из 9 успешных, остальные упираются в таймаут 150 с после 500–900 аварийных остановок. Безопасность есть, работоспособности нет.
3. **Бортовой fallback-планировщик (S4) почти не добавляет надёжности сверх S3, он добавляет скорость при обрывах.** Успех у S3 и S4 одинаковый, 100 % на 0.6 м/с. Но при обрывах 2 с стояние падает с 1.9 до 0.8 с. При обрыве ровно в момент падения коробки время 38.5 → 32.0 с (базовое 33). В комбинированном «плохом Wi-Fi» 35.6 → 31.1 с. Бортовой DWA стоит 0.5–0.7 мс на вызов против 2.9–3.6 мс у серверного MPPI (одно ядро Mac). MPPI с K = 16 вместо DWA даёт тот же успех и чуть медленнее: 35 с против 31–33 при 0.6 м/с. **Честная оговорка:** при чистой задержке S4 ≡ S3, потому что fallback включается только по тишине в канале, а не по устареванию.
4. **Полоса не узкое место, а таймаут Nav2-стиля (S1) лишь компромисс.** Uplink около 7.8 кБ/с на робота, почти всё это скан. Downlink 0.5 кБ/с у S0/S1 и 2.4 кБ/с у S2–S4. На 50 роботов выходит около 3.1 Мбит/с вверх и 1 Мбит/с вниз, что сильно ниже ёмкости Wi-Fi. Пятикратный рост downlink ради буфера ничего не стоит. S1 устраняет «слепую езду» S0 в обрывах: при GE 2 с успех 67 % → 100 %, эпизодов с контактом 6 → 0 на 0.6 м/с. Цена: робот стоит в каждом обрыве (+5–7 с), и от задержки S1 не спасает совсем, при d ≥ 150 мс S1 = S0.

**Что не моделировалось.**

- Джиттер и переупорядочивание пакетов.
- Повторная отправка (TCP или reliable QoS DDS превратили бы потери в задержку).
- Компенсация задержки на сервере (прогноз позы на RTT). Она, вероятно, дала бы S0/S1 часть выигрыша S2.
- Отдельная модель перегрузки сервера. Её можно приближённо читать как рост `d`.
- Один робот, 3–6 сидов на ячейку. Различия в 1–2 эпизода между S2, S3 и S4 статистически не значимы.

## Частота сервера с буфером траектории (второй раунд)

**Вопрос.** Если робот исполняет буфер траектории, может ли сервер планировать реже и экономить CPU? Робот по-прежнему шлёт состояние на 10 Гц, а сервер запускает MPPI только на каждом n-м тике: 10, 5 или 2.5 Гц.

**Тёплый старт.** Сравнивались два варианта:
* «наивный» — сдвиг на 1 шаг, как в Nav2;
* «выровненный» — сдвиг на реальное время между планами.

**Сетка.** 1350 эпизодов (`run_grid.py rate`, `analyze_rate.py`, полные таблицы в `tables_rate.md`):
* стратегии S1, S2, S3;
* каналы `d` = 0 / 50 / 150 мс и «плохой Wi-Fi» (150 мс + 5 % потерь + обрывы GE 2 с);
* 3 сценария, 3–6 сидов, обе скорости.

**Выводы**

1. **С буфером и бортовой проверкой (S3) сервер может планировать в 2 раза реже без потерь** на обеих скоростях: 45/45, ноль контактов, время то же. Разница появляется только при плохом Wi-Fi на 0.6 м/с: +6 с.
2. **В 4 раза реже (2.5 Гц) безопасность сохраняется** (ноль контактов в 270 эпизодах S3), но цена зависит от скорости:
   * на 0.22 м/с время то же;
   * на 0.6 м/с при задержке робот заметно медленнее: 50–58 с против 35;
   * на быстрых роботах предел ~5 Гц.
3. **Без бортовой проверки снижать частоту нельзя.** У S2 на 0.6 м/с при 2.5 Гц контакты в 6–7 эпизодах; S1 деградирует уже на 5 Гц. Буфер без проверки не защищает от того, что план устарел.
4. **Выровненный сдвиг тёплого старта не даёт стабильного выигрыша** (различия в пределах шума n = 9–18). Наивного сдвига Nav2 достаточно.
5. **Вместе с масками в Nav2** это умножает ёмкость сервера ещё в ~2 раза: 5 Гц вместо 10 при той же безопасности. В Nav2 контроллер по умолчанию работает на 20 Гц, поэтому запас, вероятно, больше; это не проверялось.

**Оговорка.** Песочница, один робот, 3–6 сидов. Сервер наивный, без прогноза позы на RTT.

## Как воспроизвести

```sh
cd ~/study/fleet-mppi/expW
./run_all.sh            # baseline, main (MPPI S0-S4), dwa (DWA S0-S3) и fbmppi (S4 с MPPI K=16) для v = 0.22 и 0.6; 3 процесса; около 75 минут
# или по частям, например:
MPP_MAX_V=0.6 uv run --project ../mpp python run_grid.py main res_main_v06.jsonl 3
python3 analyze.py > tables.md   # все таблицы ниже, плюс проверка d = 0 против run_episode
```

Один эпизод:

```sh
MPP_MAX_V=0.6 uv run --project ../mpp python -c "from mpp.runner import EpisodeConfig; from netsim import *; print(run_net_episode(EpisodeConfig(scenario='bypass', local_planner='mppi', seed=1), NetConfig(strategy='S3', link=LinkConfig(delay=0.3))))"
```

Файлы:

- `netsim.py`: модель канала, сервер и стратегии робота.
- `run_grid.py`: сетка экспериментов.
- `analyze.py`: таблицы.
- `res_*.jsonl`: сырые результаты, одна строка на эпизод.
- `tables.md`: полные таблицы.
