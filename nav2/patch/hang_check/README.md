# Проверка зависания NoiseGenerator::shutdown (10 ноября)

`stress.cpp` много раз подряд проходит цикл с `regenerate_noises=true`: initialize → 3 цикла (`setNoisedControls`, `generateNextNoises`) → `shutdown`. Если `shutdown` не вернулся за 5 с, это зависание. `CMakeLists.txt` собирает тест с исходным `noise_generator.cpp` из Nav2 (git HEAD = `2d3d1cc`; в main от 10.11 эти строки те же) и с тем же файлом плюс одна правка: `active_` и `ready_` меняются под `noise_lock_`. Код теста и исходники — в контейнере `nav2lab`, `/tmp/hc`.

Результат (Apple M4, Docker, arm64):

| сборка | прогоны | зависания |
|---|---|---|
| исходный Nav2 | 3 × 2000 циклов | 3 из 3 прогонов, на 3-м, 39-м и 55-м цикле; ещё 4 отдельных запуска — на 24, 46, 69, 79 |
| с правкой | 3 × 2000 циклов | 0 из 6000 циклов |

В момент зависания (gdb): главный поток ждёт в `std::thread::join()` внутри `NoiseGenerator::shutdown` (noise_generator.cpp:51). Поток шума спит в `noise_cond_.wait` внутри `noiseThread` (строка 105), а флаги уже `ready_ = true`, `active_ = false`. Это потерянное пробуждение: `shutdown` пишет флаги и вызывает `notify_all` без блокировки. Поэтому уведомление может прийти между проверкой условия и засыпанием потока, и поток уже не проснётся. Вдобавок это гонка данных на обычных `bool`.

В замкнутых прогонах это случилось 1 раз примерно на 4000 эпизодов со свежим шумом (раздел 18). В тесте чаще: `shutdown` вызывается сразу после `generateNextNoises`, когда поток шума как раз проверяет условие.

ThreadSanitizer на этой машине не запустился (Illegal instruction при старте; известная проблема TSan на части aarch64-ядер); гонку данных им не подтверждал.
